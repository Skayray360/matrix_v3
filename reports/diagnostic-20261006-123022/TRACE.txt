TRAZA ACOTADA — DESACTIVADA POR DEFECTO

No se creó el control operativo ni se inició un backend. Un proceso ya iniciado
antes de estos cambios no los carga automáticamente. La captura solo podrá
ocurrir en una futura ejecución del backend con estos archivos, que deberá
pasar la integridad ordinaria. No omitir esa comprobación.

Preparación local por el operador, para una prueba concreta del usuario:
crear var/diagnostics/next-answer.json con este esquema (sin estos placeholders):
{
  "user_id": "ID opaco del usuario autorizado",
  "conversation_id": "ID de su conversación de prueba",
  "question_sha256": "SHA256 UTF-8 de la pregunta exacta saneada por sanitize_user_message",
  "expires_at": "fecha ISO con zona UTC, como máximo 15 minutos en el futuro",
  "source_ids": ["source_id exacto de cada fragmento corporativo permitido"]
}

No hay comodines. Máximo ocho fuentes; no se admiten IDs __private__/. El
control debe quedar bajo los mismos permisos locales restringidos que var.
No lo prepare con datos de otras personas o conversaciones. La activación es
posterior a los controles de autorización reales del orquestador, no un sustituto
de ellos. La instrumentación no realiza búsquedas ni abre Qdrant.

El siguiente turno que coincida consume ese contenido de control una vez por
proceso. Cada captura es un evento diagnostic.answer_trace con el request_id
asignado por el servidor y la huella trace_key del control. Sin control, con
caducidad, otro usuario, otra conversación o pregunta distinta no captura.

Eventos: classified (consulta reconstruida para RAG), retrieved (IDs/páginas,
scores, hashes), packed (lo que conserva el presupuesto), ollama_payload
(modelo y opciones efectivamente enviados, hashes de mensajes, presencia exacta
de las políticas cargadas, texto saneado de las fuentes enumeradas), validated
(borrador acotado y resultado real) y retry_plan (corrección aplicada).

Los demás fragmentos llevan solo metadata; no se registra su contenido. El
historial y SQL no se vuelcan como bloques. La pregunta de recuperación puede
contener antecedentes autorizados y el borrador puede repetir datos declarados;
por eso la activación es explícita para un único turno y con límites. Se aplica
la redacción de secretos existente. No incluir conversaciones personales ajenas.

Límites: hasta 16 eventos, query 1600 caracteres, ocho extractos de hasta 1800,
borrador 2400. Las huellas y longitud corresponden al texto completo; truncated
señala expresamente si el extracto no basta. Una captura limitada no autoriza
a inferir el texto omitido. No exportar los logs operativos indiscriminadamente.

Para las reglas de población, comparar los system SHA con la construcción
actual. style_present/scope_present comparan las constantes cargadas con los
mensajes que se envían, no con una lectura posterior del archivo de disco.
Los prefijos o instrucciones adicionales siguen visibles como hashes separados.

Para cerrar diagnóstico, correlacionar retrieved -> packed -> ollama_payload ->
validated de ESA solicitud. Si falta la tabla desde retrieved, investigar la
consulta/selección. Si se pierde en packed, investigar presupuesto/selección.
Si llega íntegra, comparar el borrador rechazado y sus citas contra las reglas.
Solo entonces decidir si hay error de generación o falso rechazo.

No se programó ninguna captura ni reinicio. Este procedimiento queda preparado
para una solicitud posterior autorizada.
